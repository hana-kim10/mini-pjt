- 근거: `evaluation/latency_profile.md`, `src/agent.py`, `app.py`, `.env`

## 1. 단계별 LLM 모델

`app.py`가 `run_agent(req.question)`를 `llm` 없이 부릅니다. 그래서 모든 단계가 `build_llm(None)`(`src/agent.py:48`)으로 **같은 모델**을 새로 만듭니다.

| 단계 | 코드 위치 | 모델 | 설정 |
|---|---|---|---|
| 입력 가드 | `input_guard` `src/agent.py:122` | Claude Sonnet 4.5 | 구조화 출력 `GuardCheck` |
| 에이전트: 검색어 확장 | `collect_candidates` `src/agent.py:229` (`create_agent`) | Claude Sonnet 4.5 | 도구 호출 |
| 에이전트: 마무리("검색 완료") | 같은 에이전트 루프 | Claude Sonnet 4.5 | |
| rerank | `rerank` `src/agent.py:277` | Claude Sonnet 4.5 | 구조화 출력 `Selection` |
| 시나리오 생성 | `make_scenarios` `src/agent.py:350` | Claude Sonnet 4.5 | 구조화 출력 `ScenarioSet` |
| (LLM 아님) 임베딩 | `src/retriever.py:247` | Titan Embed v2 (`amazon.titan-embed-text-v2:0`) | |

- 실제 값은 `.env`의 `BEDROCK_MODEL_ID=us.anthropic.claude-sonnet-4-5-20250929-v1:0`, `BEDROCK_REGION=us-west-2`, `temperature=0`입니다.
- 후보가 3건보다 적으면 에이전트를 다시 돕니다(`MAX_ATTEMPTS=2`). 이때 LLM 호출이 2번 더 늘어 최대 7번이 됩니다.
- 모든 단계가 같은 모델이라, **가볍게 고르기만 하는 단계(입력 가드 3.4초, rerank 2.5초)도 Sonnet의 응답 지연을 그대로 받습니다.** 이 둘을 Haiku 같은 작은 모델로 나누면 효과가 클 것으로 봅니다. Bedrock에서 실제로 쓸 수 있는 Haiku 모델 ID는 콘솔에서 확인해야 합니다.
- 다만 정확도 기준이 빠듯합니다. 현재 하이브리드가 83/100인데, rerank 변경 후 재측정은 기준선 0.80과 같은 값이었습니다. 그래서 모델을 바꾸면 100건 평가를 다시 돌려 확인해야 합니다.

## 2. rerank 로직 리뷰 (`src/agent.py:261-298`)

### ① 후보 30건 자르기가 뒤쪽 검색어 결과를 버립니다 (품질 문제)

- `search_portal`은 검색어 하나에 최대 12건(오픈API 6 + 파일 6)을 돌려줍니다. 검색어 묶음이 3~4개면 36~48건이 모입니다.
- `cands`에는 검색어 순서대로 쌓이고, `pool = cands[:30]`(`src/agent.py:267`)이 앞에서부터 자릅니다. 그래서 **3~4번째 검색어 결과와 재확장(attempt 2) 결과가 대부분 잘립니다.**
- 그런데 에이전트 프롬프트는 상권·인구·인허가·지도처럼 "서로 다른 유형"의 검색어를 만들라고 합니다. 바로 그 다양성이 여기서 사라집니다.
- 고치는 방법: 검색어별로 한 건씩 번갈아 섞은 뒤 자릅니다. 이렇게 하면 같은 30건 안에서도 모든 검색어 결과가 들어갑니다.

### ② 입력 토큰을 줄일 수 있습니다 (속도)

- 5.8천 토큰을 30건으로 나누면 후보 하나에 약 190토큰입니다. `keywords`(`src/agent.py:270`)는 길이 제한이 없고, `summary`는 80자로 잘립니다.
- 응답은 ID 몇 개뿐이라, 이 호출 시간은 입력 처리와 첫 토큰까지의 대기가 대부분입니다.
- 키워드를 앞 5개 정도로 자르고 `org_nm`을 줄이면 입력이 절반 가까이 줄 것으로 봅니다. 작은 모델과 함께 쓰면 2.5초가 1초 안팎이 될 수 있습니다. 둘 다 추정치이고 아직 재지 않았습니다.

### ③ 지역 필터가 rerank 뒤에 있어서 LLM이 고른 결과가 버려집니다

- `run_agent`의 순서는 `rerank` → `filter_locality`(`src/agent.py:393`)입니다.
- LLM이 5건을 골라도 그중 다른 지역 지자체 데이터는 이후 단계에서 빠지고, 빈자리는 채우지 않습니다. 결과가 5건보다 적게 나옵니다.
- 사본 묶음이 아닌 지자체 단독 후보의 지역 검사를 rerank **전에** `pool`에 적용하면 두 가지가 좋아집니다. 입력 토큰이 줄고, LLM이 남은 자리를 다른 관련 후보로 채웁니다.
- 사본 묶음의 대표를 다시 고르는 일은 지금처럼 rerank 뒤에 두면 됩니다.

### ④ 모델 객체를 매번 새로 만듭니다

- `build_llm`이 단계마다 `ChatBedrockConverse`를 새로 만들어, 요청 한 건에 Bedrock 클라이언트가 4번 생깁니다.
- 한 번 만들어 재사용하면 호출마다 생기는 초기화 비용이 사라집니다. 얼마나 줄어드는지는 재 봐야 합니다.

### ⑤ 그대로 두어도 되는 부분

- 구조화 출력으로 ID만 받는 방식, 중복 제거(`dict.fromkeys`), 목록에 없는 ID를 거르는 처리는 맞게 되어 있습니다.
- 실패할 때만 검색 순서로 채우고 오픈API·파일을 섞는 것도 의도대로 동작합니다.
- 작은 문제 하나: LLM이 목록에 없는 ID만 내면 `picked`가 비고 "찾지 못했습니다" 안내로 끝납니다. 오류로 볼지, 결과 없음으로 볼지는 정책에 따라 정하면 됩니다.

### ⑥ rerank와 시나리오를 한 호출로 합치기 (선택)

- LLM 호출 한 번(약 1~2초)이 줄어듭니다.
- 대신 지역 필터와 출력 가드가 둘 사이에 있어서 흐름이 복잡해집니다. 시나리오 8.6초는 출력 생성 시간이 대부분이라, 효과는 `latency_profile.md`의 1~3번보다 작습니다.

> 적용 결과 (2026-11-20): ①·③을 적용해 100건 재측정 83/100 → 87/100 (채택). 상세는 `round2_report.md` 맨 아래 절.
