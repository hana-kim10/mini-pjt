# 질문 한 건 처리 시간 분석

- 측정일: 2026-11-20
- 모델: Bedrock Claude Sonnet 4.5 (us-west-2)
- 질문: "강남구에서 카페 창업하려고 하는데 필요한 데이터"
- 방법: `run_agent` 의 단계 함수, 검색 함수, LLM 호출에 시간 측정을 붙여 한 건씩 실행

## 30초가 어디서 걸리는지

아래는 서버가 이미 한 번 돈 상태(데워진 상태)에서 잰 값이고, 총 25.4초입니다.

| 단계 | 시간 | 비고 |
|---|---|---|
| 입력 가드 LLM | 3.4s | |
| 에이전트: 검색어 확장 LLM | 3.2s | 입력 약 2천 토큰, 출력 약 290토큰 |
| 검색 도구 4개 병렬 | ~5s | 하이브리드 검색과 임베딩 |
| 에이전트: 마무리 LLM | 1.7s | **"검색 완료"만 출력하는데 입력이 1.8만 토큰** |
| rerank LLM | 2.5s | 입력 약 5.8천 토큰 |
| **시나리오 생성 LLM** | **8.6s** | **가장 큰 병목.** 출력 약 720토큰 |

- LLM 호출 다섯 번이 약 19.5초로 전체의 4분의 3을 차지합니다. 검색 자체는 약 5초입니다.
- 서버를 띄운 뒤 첫 요청은 데이터와 인덱스를 불러오느라 약 6초가 더 걸려 31.3초가 나왔습니다. 체감 30초는 이 경우일 가능성이 있습니다.

## 줄일 수 있는 곳 (효과 큰 순)

1. **시나리오 생성 (8.6초)**: 출력 길이를 줄이거나, 추천 목록을 먼저 보여 주고 시나리오는 나중에 채웁니다. 시나리오를 1개만 만들면 약 4초가 줄 것으로 봅니다.
2. **입력 가드를 검색과 동시에 실행 (약 3초 절약)**: 가드가 차단하면 검색 결과를 버립니다. → 적용함 (요청 19.5초 → 16.6초)
3. **에이전트 마무리 호출 없애기 (1.7초 절약)**: 검색 도구 결과를 받은 뒤 에이전트를 바로 끝내도록 설정합니다(`return_direct`). 질문 한 건의 토큰이 약 60% 줄어 평가 때 하루 토큰 한도 문제에도 도움이 됩니다. → 적용함 (아래 비교)

세 가지를 다 하면 데워진 상태에서 25초가 15초 안팎으로 줄 것으로 봅니다. 2·3번은 적용했고 1번(시나리오)은 아직입니다.

## 마무리 호출 제거 전후 비교 (3번)

- 방법: 평가셋 12건(1,2,3,5,8,11,12,19,21,24,26,28)으로 `collect_candidates` 를 두 방식으로 번갈아 실행 (us-west-2, 데워진 상태). 기존 = 도구 실행 후 마무리 LLM 호출, 변경 = 두 도구 `return_direct=True`
- 변경 내용: `src/tools.py` 의 두 도구에 `@tool(return_direct=True)`. 프롬프트는 그대로이고, 필요하면 `False` 로 되돌려 끌 수 있습니다(코드 주석 참고)

| | 기존 | 변경 |
|---|---|---|
| 검색 단계 평균 | 6.36s | **4.97s** (−1.39s) |
| 검색 단계 LLM 호출 | 2회 | 1회 |
| 마무리 호출이 도구를 다시 부른 경우 | 0/12 (매번 "검색 완료"만 출력) | 해당 없음 |
| 검색 실패 | 0/12 | 0/12 |
| 후보 수 | 9건 같음, 3건은 1~2개 차이 | |

- 후보 수 차이는 검색어 확장 LLM이 실행마다 다른 검색어를 만드는 데서 오며, 같은 방식으로 다시 돌려도 생기는 수준입니다.
- 전체 요청(데워진 상태, "베이커리카페를 창업하고 싶다" 등): 기존 17.3~18.4s, 변경 15.2~16.9s.
- 같은 질문의 추천 목록이 실행마다 달라지는 현상(베이커리 질문에서 인허가 데이터가 자주 빠짐)은 두 방식 모두에서 나타났습니다. 이번 변경 때문이 아니라 검색어 확장 단계의 변동입니다.
- 100건 재평가는 하지 않았습니다. 후보를 모으는 방식은 그대로이고 사용하지 않던 마무리 응답만 없앴기 때문입니다.
